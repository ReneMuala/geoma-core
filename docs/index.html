geoma documentation

A compact C++20 toolkit for loading real-world road networks, repairing their graphs, and finding routes across them. If you can open a file and draw an SVG, you can use geoma.

Get started See a full example

#Start hereWhat is geoma?

geoma treats a road network the way it really is: a graph. Every intersection is a vertex — a point in 2D space — and every road segment between two intersections is an edge. A collection of these vertices is called a world, and it is the one datatype everything in the library works with.

That single idea keeps geoma approachable: there are no scene graphs, no entity systems and no framework to learn. You import data into a world, optionally clean it up, ask the navigator for routes, and export the result — as an SVG you can open in a browser, a compact binary blob, or a plain-text edge list.

Real-world data in

Reads OpenStreetMap .osm XML and GeoJSON files — including country-sized extracts, parsed on a worker thread pool — plus geoma's own binary format for near-instant reloads.

Graph repair built in

Merges duplicate points, snaps dead-ends onto edges and splits crossings — the messy parts of real map data, handled in place.

Budgeted routing

A greedy best-first search with flexible budgets — N solutions, a time limit, or both — and an optional frontier cap for very large worlds.

Visual output

One call renders the whole world to SVG with hoverable roads — well suited to inspecting your data visually while debugging.

Audience

Who is this for? Students and developers who want to experiment with routing, map data and graph algorithms without adopting a heavyweight GIS stack. Basic C++ knowledge is sufficient.

#The big pictureHow it works

Everything you do with geoma follows the same four-stage pipeline:

1
Import

OSM, GeoJSON or native binary → a world of vertices

→
2
Clean up

dissolve, close, subdivide, decouple

→
3
Navigate

find routes from A to B

→
4
Export

SVG, binary, or edge list

Every stage is optional and independent. You can import and immediately export just to see your data; you can skip cleanup entirely; you can even build a world completely by hand with vertex::make and vertex::join and never touch a file at all.

Key type

The one type to remember: std::list<std::shared_ptr<geoma::core::vertex>> — that is a "world". Nearly every function in the library takes or returns one.

#Getting startedBuild & run

Requirements

  • A C++20 compiler (MSVC, GCC or Clang — the project builds on Windows and Linux)
  • xmake or CMake ≥ 3.15
  • Four small dependencies, fetched automatically by xmake: rapidxml, jsoncpp, lunasvg, fmt

Build with xmake (recommended)

terminal
xmake                # configure + build in one step
xmake run geoma       # run the demo program

Build with CMake

terminal
cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build
./build/geoma
Note

The CMakeLists.txt in the repository is autogenerated by xmake. Do not edit it by hand; change xmake.lua instead.

What the demo does

main.cpp contains several demo routines; edit main() to switch between them:

  • port_path_check() — currently wired in. Loads the native binary port.gbm, then routes across it with the frontier capped via navigator::flags{.next_steps_limit = 3} and writes port.svg.
  • port_test() — the full GeoJSON pipeline: import, per-step cleanup statistics, routing with a 10-route / 2-second budget, then an SVG render.
  • denoise_and_shrink_map() — iterative cleanup passes over a GeoJSON extract, followed by a binary round-trip: it exports port.gbm, re-imports it and verifies the result with experimental::equal.
  • pontagea_test() — OSM import, routing, SVG plus binary export.
  • moz_test() — one-time bulk conversion of a country-sized OSM file to the binary format.

#TutorialYour first route

A complete, real program: load a map, clean it, route across it, save a picture.

my_first_route.cpp
#include "geoma.hpp"                    // core, osm importer, svg/links exporters, experimental
#include "modules/importer/geojson.hpp"   // not pulled in by the umbrella header
#include <fmt/core.h>

int main()
{
    // 1. Load a road network into a "world"
    auto world = geoma::importer::geojson::import("city.geojson");

    // 2. Clean the graph so routes look sane
    geoma::experimental::decouple(world);                        // drop duplicated links
    auto merged = geoma::experimental::dissolve(world, 5e-5);   // merge near-duplicate points
    auto closed = geoma::experimental::close(world, 1e-4);      // snap dead-ends onto edges

    // 3. Define the journey: A to B, at most 10 routes within 2 seconds
    auto nav    = geoma::core::navigator::make(
                      geoma::core::vertex::make(-19.8209, 34.8341),
                      geoma::core::vertex::make(-19.8161, 34.8387));
    auto budget = geoma::core::incremental_timed_counter::make(10, std::chrono::seconds(2));

    geoma::core::navigator::solutions solutions;
    geoma::core::navigator::navigate(nav, world, budget, solutions);

    // 4. Inspect the result
    fmt::println("found {} route(s)", solutions.size());
    geoma::exporter::svg::export_(world, "city.svg", 1e5);
    return 0;
}

A few notes on what just happened:

  • The umbrella header geoma.hpp includes geoma::core, the OSM importer, the SVG and links exporters, and geoma::experimental. The GeoJSON and native-binary modules are included separately, as shown above.
  • dissolve and close take thresholds in coordinate units. For latitude/longitude data, 5e-5 degrees is roughly 5 meters — tune these per dataset.
  • The counter is the search's stop condition. Here it allows 10 routes or 2 seconds, whichever comes first, so the program finishes quickly even on large maps.
  • navigate accepts an optional fifth argument, navigator::flags. Setting .next_steps_limit = N keeps only the N most promising candidates per search level — a significant speed-up on dense graphs, at the cost of exploring fewer alternatives.
  • export_'s last argument is the zoom: pixels per coordinate unit. 1e5 is a good starting point for city-scale degree coordinates.
  • Each solution is a std::list of vertices ordered from target back to origin — iterate it to walk the route.
Minimal start

To start even smaller, skip the file entirely and build a world by hand:

tiny_world.cpp
std::list<std::shared_ptr<geoma::core::vertex>> world;

auto a = geoma::core::vertex::make(0, 0);
auto b = geoma::core::vertex::make(1, 0);
auto c = geoma::core::vertex::make(1, 1);
geoma::core::vertex::join(a, b);  geoma::core::vertex::join(b, a);  // two-way edge
geoma::core::vertex::join(b, c);  geoma::core::vertex::join(c, b);

world = { a, b, c };
geoma::exporter::svg::export_(world, "tiny.svg", 100);  // renders a triangle-less L

#LearnCore concepts

Worlds and vertices

A vertex (geoma::core::vertex) is a 2D point plus a list of neighbors. Edges live inside the vertices themselves: a having b in its neighbor list means "there is an edge a→b". Two important details:

  • vertex::join(a, b) creates a one-way link. The importers always call it twice to make two-way roads — do the same unless you are modelling one-way streets.
  • vertex::equals compares coordinates exactly, not memory addresses. Two distinct vertices at the same coordinates compare equal but remain separate objects.

The navigator

navigator::navigate is a greedy best-first search. It snaps your origin and target to the closest vertices in the world, then expands the frontier level by level, sorting candidate steps by remaining distance to the target so the most promising branches are explored first. When a step lands on the target's vertex, the chain of steps is flattened into a route and recorded.

Because it is guided and budgeted rather than exhaustive, it answers quickly on large worlds — "a good route now" rather than "a provably optimal route eventually". The optional navigator::flags{.next_steps_limit = N} argument truncates each level's sorted frontier to its best N entries, which bounds the per-level work on dense graphs.

Counters: the search's stop condition

Counters decide when navigate stops. All implement the same small interface:

CounterStops when…Make it with
incremental_counterN solutions have been foundmake(limit)
timed_countera wall-clock deadline passesmake(duration)
incremental_timed_countereither of the above — the safe defaultmake(limit, duration)

Need different behavior? Derive from geoma::core::counter and implement done() / count() — the navigator will use it as-is.

Steps

step is the navigator's internal bookkeeping: one step means "standing on this vertex, having arrived from that predecessor". Steps link backwards, so a finished route is recovered by walking the predecessor chain — step::walkthrough does exactly that. You rarely touch steps yourself, but they are exposed for experimentation.

#LearnGraph cleanup ops

Real map data is messy. The geoma::experimental namespace holds four in-place repair operations, each returning the number of elements it touched. They are the reason the demo routes look clean.

Recommended order

Mirroring the demo: decouple → dissolve → close → subdivide → decouple again. Measuring the world before and after with count() tells you exactly how much each step repaired.

#LearnData formats

Importing

FormatFunctionWhat it reads
OpenStreetMap XML importer::osm::import <node> elements become vertices; <way> elements tagged highway link their consecutive <nd> nodes. Nodes with action="delete" are skipped; vertices never referenced by a highway are dropped. Parsed on a thread pool.
GeoJSON importer::geojson::import Every feature's coordinate arrays become paths: consecutive positions are joined two-way. Vertices are deduplicated by coordinate. Coordinates are read as [lon, lat] and stored as x = lat, y = lon.
Native binary importer::native::import geoma's own compact dump (layout below). Validates the checkpoint and the byte-size sentinel while loading; returns an empty list on any inconsistency. The fastest way to load a world.

The XML and JSON importers load the whole file into memory first (a warning is printed above ~1 GB), so very large extracts need RAM to match. The recommended workflow for bulk data is to convert once with the OSM importer and reload through native::import afterwards — see moz_test and port_path_check in main.cpp.

Exporting

FormatFunctionOutput
SVGexporter::svg::export_Browser-ready drawing: orange roads (cyan on hover), blue dots labeled with coordinates and degree.
Native binaryexporter::native::export_Compact graph dump — layout below. Fast to write, fast to reload.
Edge listexporter::links::export_One a -> b text line per directed edge. Useful for debugging and diffing.

Native binary layout

OrderTypeField
1uint64Vertex count N (header)
2N × double, doublex, y of each vertex, in list order
3uint64N again (checkpoint after the vertex block)
4pairs of uint64One pair per directed edge: source index, destination index
5uint64Total file size in bytes (footer integrity sentinel)
Warning

The exporter fails with a "ghost vertex" error if a vertex's neighbor is not itself in the world list — every neighbor must be exported for indices to stay valid. Values are written with the host's endianness and unsigned long long width, so files are not portable across differing platforms.

#HelpFAQ

Where do I get data to feed it?

Any .osm export. Start small — a neighborhood is plenty while learning the API.

My SVG is blank, tiny or enormous. Why?

Three usual suspects: an empty world (import failed — check the log lines), a zoom that does not match your coordinate scale (try 1e5 for degrees), or a zero-extent world (all points identical — the exporter refuses that case).

The navigator finds no solutions. Why?

Check in order: (1) is the world non-empty? (2) are origin and target actually near the world — they are snapped to the closest vertices, but if the graph is disconnected there may be no path at all; (3) is your budget generous enough? Try incremental_timed_counter::make(100, 30s). Conversely, if searches are slow, cap the frontier with navigator::flags{.next_steps_limit = 3}.

What units are the thresholds in?

Whatever your coordinates are in. For lat/lon data, 1e-5 degrees ≈ 1.1 m at the equator, so 5e-5 ≈ 5 m — the values used in the demos. There is no geodesic math: distances are plain Euclidean on the raw coordinates, which is adequate at city scale.

Are edges one-way or two-way?

The graph supports both; join is one-way and the importers call it twice, so imported worlds are two-way. For one-way streets, build edges with single join calls.

Can I use geoma as a library instead of the demo binary?

Yes — include src/geoma.hpp (plus modules/importer/geojson.hpp or modules/importer/native.hpp when needed), compile the src/ sources with your project (C++20, plus the four dependencies), and follow the tutorial above. The demo main.cpp is example code you are welcome to gut.
