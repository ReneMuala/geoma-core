Welcome to geoma 👋

A small, friendly C++ toolkit for loading real-world road networks, cleaning them up, and finding routes across them. If you can open a file and draw an SVG, you can use geoma.

Get started → See a full example

Start hereWhat is geoma?

geoma treats a road network the way it really is: a graph. Every intersection is a vertex — a point in 2D space — and every road segment between two intersections is an edge. A collection of these vertices is called a world, and it's the one datatype everything in the library works with.

That single idea makes geoma very approachable: there are no scene graphs, no entity systems, no mandatory build scripts to learn the internals of. You import data into a world, optionally clean it up, ask the navigator for routes, and export the result — as an SVG you can open in a browser, a compact binary blob, or a plain-text edge list.

🗺️ Real-world data in

Reads OpenStreetMap .osm XML and GeoJSON files, including country-sized extracts — parsed on a worker thread pool.

🧹 Graph repair built in

Merges duplicate points, snaps dead-ends onto edges and splits crossings — the messy bits of real map data.

🧭 Greedy routing

A best-first search that walks the graph toward your target, with flexible budgets: N solutions, a time limit, or both.

🎨 Visual output

One call renders the whole world to SVG with hoverable roads — perfect for debugging your data visually.

💡 Who is this for? Students and developers who want to experiment with routing, map data and graph algorithms without dragging in a heavyweight GIS stack. If you know basic C++, you already know enough.

The big pictureHow it works

Everything you do with geoma follows the same four-stage pipeline:

1
Import

OSM or GeoJSON → a world of vertices

→
2
Clean up

dissolve, close, subdivide, decouple

→
3
Navigate

find routes from A to B

→
4
Export

SVG, binary, or edge list

Every stage is optional and independent. You can import and immediately export just to see your data; you can skip cleanup entirely; you can even build a world completely by hand with vertex::make and vertex::join and never touch a file at all.

📌 The one type to remember: std::list<std::shared_ptr<geoma::core::vertex>> — that's a "world". Every function in the library takes or returns one.

Getting startedBuild & run

What you need

  • A C++20 compiler (MSVC, GCC or Clang — the project builds on Windows and Linux)
  • xmake or CMake ≥ 3.15
  • Four small dependencies, fetched automatically by xmake: rapidxml, jsoncpp, lunasvg, fmt

Build with xmake (recommended)

terminal
xmake                # configure + build in one step
xmake run geoma       # run the demo program

Build with CMake

terminal
cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build
./build/geoma
ℹ️ The CMakeLists.txt in the repo is autogenerated by xmake — don't edit it by hand; change xmake.lua instead.

What the demo does

Out of the box, main.cpp runs port_test(): it loads a GeoJSON extract, runs the full cleanup pipeline with per-step statistics, routes between two coordinates and writes port.svg. Open that SVG in a browser and you'll see your map — orange roads that light up cyan when you hover them. The other routines (pontagea_test, moz_test) show OSM importing and bulk binary conversion; comment/uncomment calls in main() to switch.

5-minute tutorialYour first route

Here is a complete, real program. Load a map, clean it, route across it, save a picture.

my_first_route.cpp
#include "geoma.hpp"   // one header for everything

int main()
{
    // 1️⃣  Load a road network into a "world"
    auto world = geoma::importer::geojson::import("city.geojson");

    // 2️⃣  Tidy the graph so routes look sane
    geoma::experimental::decouple(world);                        // drop duplicated links
    auto merged = geoma::experimental::dissolve(world, 5e-5);   // merge near-duplicate points
    auto closed = geoma::experimental::close(world, 1e-4);      // snap dead-ends onto edges

    // 3️⃣  Set up a journey: from A to B, max 10 routes, 2-second budget
    auto nav     = geoma::core::navigator::make(
                       geoma::core::vertex::make(-19.8209, 34.8341),
                       geoma::core::vertex::make(-19.8161, 34.8387));
    auto budget  = geoma::core::incremental_timed_counter::make(10, std::chrono::seconds(2));

    geoma::core::navigator::solutions solutions;
    geoma::core::navigator::navigate(nav, world, budget, solutions);

    // 4️⃣  Show the result
    fmt::println("found {} route(s)", solutions.size());
    geoma::exporter::svg::export_(world, "city.svg", 1e5);
    return 0;
}

That's genuinely the whole API shape. A few notes on what just happened:

  • dissolve and close take thresholds in coordinate units. For latitude/longitude data, 5e-5 degrees is roughly 5 meters — you'll tune these per dataset.
  • The counter is the search's stop button. Here it allows 10 routes or 2 seconds, whichever comes first — so the program always finishes quickly even on huge maps.
  • export_'s last argument is the zoom: pixels per coordinate unit. Higher zoom, bigger picture. 1e5 is a good start for city-scale degree coordinates.
  • Each found solution is a std::list of vertices from target back to origin — iterate it to get the route.
🧪 Want to start even smaller? Skip the file entirely and build a world by hand:
tiny_world.cpp
std::list<std::shared_ptr<geoma::core::vertex>> world;

auto a = geoma::core::vertex::make(0, 0);
auto b = geoma::core::vertex::make(1, 0);
auto c = geoma::core::vertex::make(1, 1);
geoma::core::vertex::join(a, b);  geoma::core::vertex::join(b, a);  // two-way edge
geoma::core::vertex::join(b, c);  geoma::core::vertex::join(c, b);

world = { a, b, c };
geoma::exporter::svg::export_(world, "tiny.svg", 100);  // it renders! 🎉

LearnCore concepts

🌍 Worlds and vertices

A vertex (geoma::core::vertex) is a 2D point plus a list of neighbors. Edges live inside the vertices themselves: a has b in its neighbors list means "there is an edge a→b". Two important details:

  • vertex::join(a, b) creates a one-way link. The importers always call it twice to make two-way roads — you should too, unless you model one-way streets.
  • vertex::equals compares coordinates exactly, not memory addresses. Two different vertices at the same coordinates are "equal" but still distinct objects.

🧭 The navigator

navigator::navigate is a greedy best-first search. It snaps your origin and target to the closest vertices in the world, then expands the frontier level by level, always sorting candidate steps by "distance remaining to the target" so the most promising branches are tried first. When a step lands on the target's vertex, the chain of steps is flattened into a route and recorded.

Because it's guided and budgeted rather than exhaustive, it answers fast on big worlds — think "good route now" rather than "provably optimal route eventually".

⏱️ Counters: the search's stop button

Counters decide when navigate gives up. All implement the same tiny interface:

CounterStops when…Make it with
incremental_counterN solutions have been foundmake(limit)
timed_countera wall-clock deadline passesmake(duration)
incremental_timed_countereither of the above — the safe defaultmake(limit, duration)

Need different behavior? Derive your own from geoma::core::counter and implement done() / count() — the navigator will happily use it.

🪜 Steps

step is the navigator's internal bookkeeping: one step = "I'm standing on this vertex, having come from that predecessor". Steps link backwards, so a finished route is recovered by walking the predecessor chain — step::walkthrough does exactly that. You rarely touch steps yourself, but they're exposed for experimentation.

LearnGraph cleanup ops

Real map data is messy. The geoma::experimental namespace holds four in-place repair operations, each returning the number of elements it touched. They're the reason demo routes look clean.

🔧 Recommended order (mirrors the demo): decouple → dissolve → close → subdivide → decouple again. Counting vertices before and after with count() tells you exactly how much each step repaired.

LearnData formats

📥 Importing

FormatFunctionWhat it reads
OpenStreetMap XML importer::osm::import <node> elements become vertices; <way> elements tagged highway link their consecutive <nd> nodes. Nodes with action="delete" are skipped; isolated vertices are dropped. Parsed on a thread pool.
GeoJSON importer::geojson::import Every feature's coordinate arrays become paths: consecutive positions are joined two-way. Vertices are deduplicated by coordinate. Coordinates are read as [lon, lat] and stored as x = lat, y = lon.

Both importers load the whole file into memory first (a warning is printed above ~1 GB), so very large extracts need RAM to match. The OSM importer is your friend for bulk conversion: see moz_test in main.cpp for converting a country-sized file to the binary format once, then loading instantly afterwards.

HelpFAQ

Where do I get data to feed it?

Any .osm export (e.g. from Overpass Turbo or Geofabrik extracts) or any GeoJSON with linear features. Start small — a neighborhood is plenty while you learn the API.

My SVG is blank / tiny / enormous. What gives?

Three suspects: an empty world (import failed — check the log lines), a zoom that doesn't match your coordinate scale (try 1e5 for degrees), or a zero-extent world (all points identical — the exporter refuses that politely).

The navigator finds no solutions. Why?

Check in order: (1) is the world non-empty? (2) are origin and target actually near the world — they're snapped to the closest vertices, but if the graph is disconnected there may be no path at all; (3) is your budget generous enough? Try incremental_timed_counter::make(100, 30s) and see what turns up.

What units are the thresholds in?

Whatever your coordinates are in. For lat/lon data, 1e-5 degrees ≈ 1.1 m at the equator, so 5e-5 ≈ 5 m — the values used in the demos. There is no geodesic math: distances are plain Euclidean on the raw coordinates, which is fine at city scale.

Are edges one-way or two-way?

The graph itself supports both; join is one-way and the importers call it twice, so imported worlds are two-way. If you want one-way streets, build them with single join calls.

Can I use geoma as a library instead of the demo binary?

Yes — include src/geoma.hpp, compile the src/ sources with your project (C++20, plus the four dependencies), and follow the tutorial above. The demo main.cpp is just example code you're welcome to gut.
